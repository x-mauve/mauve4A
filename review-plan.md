# review-plan.md — план ревью системы плагинов mauve

План разбивает ревью системы плагинов на 6 прогонов и один сводный. Каждый прогон
идёт отдельной сессией со своим скоупом. Карта файлов лежит в `plugins-spec.md`,
этот файл задаёт только порядок работы, её границы и формат результата.

## Общие правила для всех этапов

**Цель.** Нужно найти уязвимости в модели разрешений и баги корректности и
надёжности. Стиль, нейминг, рефакторинг и «можно было бы красивее» не ищем.

**Модель угроз.** Атакующие по убыванию приоритета:

1. **Вредоносный плагин** с частью выданных прав. Он хочет получить больше: другое
   право, доступ к данным другого плагина, отключение гейта или подделку грантов.
   Это главный сценарий.
2. **Вредоносный файл**: `.plugin`, `.eaf`, бэкап или ссылка, которые пользователь
   открыл. Он хочет выполнить код или получить права без явного согласия
   пользователя, либо добиться, чтобы UI показал меньше, чем плагин реально может.
3. **Другое приложение или процесс на устройстве**: интенты, `content://`,
   loopback-порты.
4. **Кривой, но не злой плагин**: крэш или ANR хоста, порча состояния, утечки,
   safe mode, который не спасает.

Вне скоупа: рут или скомпрометированное устройство, а также права, которые по
определению дают полный доступ к JVM. Если плагину явно выдали такое право, «он
может всё» — не находка. Находка — когда то же самое достижимо без этого права или
когда UI преуменьшает, что даёт право.

**Источник истины.** Только код. Внешнюю документацию exteraGram не читать.
Тесты в `tests/` можно читать точечно, чтобы понять задуманное поведение, но не
целиком.

**Экономия лимитов.**

- Файлы из скоупа этапа читать полностью. За пределами скоупа — только `grep` и
  чтение нужных фрагментов. Большие апстрим-файлы (`ChatActivity`,
  `ConnectionsManager` и т.п.) целиком не открывать.
- Не перечитывать то, что уже описано в handoff предыдущих этапов. Если handoff
  противоречит коду, верь коду и отметь расхождение.
- Код не править. Результат этапа — только файл с находками.
- Не сходится с выводом из handoff — один раз проверь фрагмент и иди дальше,
  без расследований на весь проект.

**Результат этапа** — файл `review/NN-<slug>.md`:

```markdown
# Этап N — <название>

## Находки

### SN-01 [Critical|High|Medium|Low|Info] Короткий заголовок
- Где: `path/File.java:123` (+ связанные места)
- Сценарий: кто атакует, предусловия (какие права уже есть), шаги, результат
- Уверенность: confirmed (путь прослежен по коду) | likely | speculative
- Фикс: 1–2 предложения, без кода

## Проверено, проблем нет
Короткий список того, что смотрел и счёл корректным, чтобы следующие этапы не
перепроверяли.

## Handoff
До ~40 строк фактов (не находок), которые нужны следующим этапам: как устроена
атрибуция, где хранится ключ подписи, какие права эквивалентны полному доступу,
какие точки входа Python → Java существуют, и т.п.
```

Шкала: **Critical** — обход разрешения без гранта или выполнение кода из файла
без согласия. **High** — повышение прав при частичном гранте, подделка грантов,
крэш-петля без выхода. **Medium** — утечка данных между плагинами, UI вводит в
заблуждение. **Low/Info** — остальное.

**Шаблон промпта для прогона:**

> Прочитай `review-plan.md` (общие правила и этап N) и `plugins-spec.md`. Прочитай
> handoff-секции из `review/*.md` предыдущих этапов. Выполни этап N, результат
> запиши в `review/NN-<slug>.md`. Код не меняй.

## Порядок и приоритет

Этапы идут по убыванию ценности. Если лимиты кончились, останавливайся после
любого этапа: самое важное уже будет покрыто. Этапы 1–3 зависят друг от друга
через handoff. Этапы 4–6 опираются только на handoff этапа 1, их можно гонять в
любом порядке.

| # | Этап | Объём, строк | Приоритет |
|---|---|---|---|
| 1 | Модель разрешений: гейты и гранты | ~4.7k | обязательно |
| 2 | Побег из песочницы через JVM | ~5.9k | обязательно |
| 3 | Python-рантайм и изоляция плагинов | ~6.7k | обязательно |
| 4 | Недоверенный ввод и цепочка поставки | ~6k | высокий |
| 5 | Контроллер, диспатч хуков, интеграция, надёжность | ~6.7k | средний |
| 6 | UI, настройки, shim-слой | ~6k | низкий, опционально |
| 7 | Сводка | только `review/*.md` | дешёвая модель |

## Этап 1 — Модель разрешений: гейты и гранты

Фундамент. Остальные этапы опираются на его handoff, поэтому handoff тут важнее
обычного.

Скоуп:

- `app/exteraless/plugins/`: `PluginPermissions`, `PluginTrustLevel`,
  `PluginGrantStore`, `SignedGrantPreferences`, `PluginSinkGate`, `PluginRuntime`,
  `PythonThreadState`, `PluginAuditJournal`, `PluginDenialNotice`.
- `ui/PluginPermissionsActivity`, `ui/PluginPermissionCell`: показывает ли экран
  реальное состояние и делает ли переключатель то, что обещает.
- Python: `extera_utils/audit_gate.py`, `extera_utils/thread_state.py`.

Ключевые вопросы:

- Полнота покрытия стоков. Права применяются в двух местах. Python может звать
  Java напрямую через Chaquopy, мимо audit hooks, а Java-код плагина может
  обойти Python-гейт. Закрывают ли два гейта пробелы друг друга? Составь
  таблицу «право → какие стоки его применяют (Python / Java)» и отметь дыры.
- Атрибуция. Правильно ли определяется, чей код сейчас выполняется: в колбэках,
  на других потоках, в `Handler.post`, в слушателях, таймерах, отложенных
  задачах? Может ли плагин выполниться как «хост» или как другой плагин?
- Гранты: где ключ подписи, доступен ли он плагину, что подписывается
  (привязка к pluginId и версии/хешу кода?), что происходит при обновлении плагина
  и при невалидной подписи (fail-open или fail-closed).
- TOCTOU между проверкой и действием, кэширование решений, гонки при смене гранта
  на лету.
- В handoff: список прав, которые по сути дают полный доступ к JVM, механизм
  атрибуции, все точки, где принимается решение «разрешить / запретить».

## Этап 2 — Побег из песочницы через JVM

Вопрос этапа: может ли плагин с ограниченными правами достать JVM без ограничений
и через это отключить гейт, переписать гранты или повесить хук на сам гейт.

Скоуп:

- Python: `hook_utils.py`, `extera_utils/classes.py`, `extera_utils/class_aliases.py`,
  `android_utils.py` (прокси слушателей).
- Java: `utils/ClassProxyFactory`, `xposed/*` (особенно `HookGate`, `XposedHooks`,
  `HookFilter`, `PyMethodHook`, `PyMethodReplacement`), `ClassAliases`,
  `PluginServices`, `PluginMediaServices`, `PluginViewProxies`.

Ключевые вопросы:

- Рефлексия: можно ли добраться до приватных полей и статиков `PluginSinkGate`,
  `PluginGrantStore`, `PluginRuntime` и т.п. и до `setAccessible`, `Unsafe`,
  `MethodHandles`?
- Хуки: проверяет ли `HookGate` цель хука (можно ли захукать сам гейт, систему
  плагинов, `ClassLoader`)? Кто проверяется при установке хука, а кто — при его
  срабатывании?
- Class proxy и генерация байткода: можно ли сгенерировать подкласс или прокси,
  который выполняется вне атрибуции плагина или подменяет класс системы?
- Алиасы: можно ли через алиас получить класс, который иначе запрещён?
- `PluginServices`: не отдаёт ли что-то, что даёт больше, чем грант?

## Этап 3 — Python-рантайм и изоляция плагинов

Все плагины живут в одном CPython. Вопрос этапа: что один плагин может сделать
с другим и с самим рантаймом.

Скоуп:

- Python: `extera_utils/plugin_loader.py`, `base_plugin.py`,
  `extera_utils/metadata_parser.py`, `plugin_settings.py`, `file_utils.py`,
  `extera_utils/hook_profile.py`.
- Java: `PythonPluginsEngine`, `PythonBridge`.

Ключевые вопросы:

- Целостность гейта изнутри Python: можно ли изменить состояние `audit_gate`
  (глобалы модуля, `sys.modules`, `builtins`, monkeypatch SDK, `gc`, фреймы,
  `ctypes`)? Хук PEP 578 снять нельзя, а логику, на которую он опирается, — может
  быть.
- Изоляция между плагинами: доступ к модулю, объектам, настройкам и файлам
  другого плагина; подмена общих модулей SDK для всех.
- Жизненный цикл: остаются ли после `unload` хуки, потоки, слушатели, меню,
  прокси? Работает ли «выключенный» плагин дальше? Что происходит при исключении
  в `on_plugin_load`?
- `metadata_parser`: действительно ли ничего не исполняется? Совпадает ли то, что
  он видит, с тем, что реально загрузится (`__id__` из AST против рантайма,
  подмена `__id__` и коллизии ID)?
- `plugin_settings` / `file_utils`: path traversal, симлинки, выход за директорию
  плагина.

## Этап 4 — Недоверенный ввод и цепочка поставки

Вопрос этапа: как код попадает на устройство и получает права, и где согласие
пользователя можно обойти или подделать.

Скоуп:

- Java: `PluginInstallHelper`, `ui/PluginInstallBottomSheet`, `PluginCapabilityScan`,
  `PluginsBackup`, `ui/components/PluginReviewTools`, `ui/components/PluginAiReview`,
  `ui/components/PluginFileViewer`.
- Python: `extera_utils/capability_scan.py`, `pip_controller.py`, `dev_server.py`,
  `elyx_runtime/*`, `elyxcore/__init__.py`.
- Только grep и фрагменты: `AndroidManifest.xml` (intent-filter `.plugin`),
  `LaunchActivity` (открытие файлов, safe mode), `EtgBackup`, `SettingsHelper`,
  dev-сервер в `PythonPluginsEngine`.

Ключевые вопросы:

- Установка: `content://` и URI, имена файлов, перезапись существующего плагина
  (сохраняются ли гранты старого при подмене кода?), молчаливая установка без
  шита.
- Elyx-архивы: zip slip, симлинки, zip-бомбы, wheels с нативным кодом, refmap,
  изоляция namespace.
- Скан возможностей: насколько легко обойти статический скан (`getattr`, `exec`,
  кодировки, импорт через строку)? Не подаёт ли UI его результат как гарантию?
- Бэкап и импорт: можно ли через бэкап протащить плагин сразу с грантами, минуя
  подпись?
- `pip_controller`: откуда качает, проверяются ли хеши, что с `setup.py` и
  нативными колёсами, в какой директории ставится.
- Dev-сервер: действительно ли только developer mode и 127.0.0.1, есть ли
  аутентификация (любое приложение на устройстве может стучаться в loopback),
  что можно сделать командами.
- AI-ревью: что и куда отправляется, и может ли плагин повлиять на результат
  ревью (prompt injection в исходнике).

## Этап 5 — Контроллер, диспатч хуков, интеграция, надёжность

Здесь в основном корректность и надёжность (атакующий 4), а также утечки данных
через хуки.

Скоуп:

- Java: `PluginsController`, `PluginsWatchdog`, `Plugin`, `PluginsConstants`,
  `HookResult`, `HookTargetCache`, `MenuItemRecord`, `JsonUtils`, `PluginLog`,
  `menus/*`, `intents/*`, `files/*`.
- Python: `client_utils.py`, `intents.py`.
- Только grep по `PluginsController` / `app.exteraless.plugins`: точки интеграции
  из раздела «Java: точки интеграции» в `plugins-spec.md`, включая
  `WalletPluginFreeze`, `CrashLog`, `QuickToggleActivity`.

Ключевые вопросы:

- Нужны ли права на хуки отправки, запросов и апдейтов? Видит ли плагин секретные
  чаты, экран кошелька и другие чувствительные данные без соответствующего
  права? Работает ли заморозка на экране кошелька, или её можно обойти?
- Модификация и отмена запросов: может ли плагин подменить запрос так, чтобы хост
  отправил то, чего пользователь не видел?
- Потоки и GIL: дедлоки (UI-поток ждёт Python, а Python ждёт UI-поток), ANR,
  вызовы на неправильном потоке, исключения из Python, которые роняют хост.
- Watchdog и safe mode: гарантирует ли safe mode, что не исполняется ни строчки
  плагина? Может ли плагин помешать автоотключению или крэш-петля оказаться без
  выхода?
- Приоритеты и порядок хуков, повторная регистрация, утечки после выключения.
- Интенты и ссылки: может ли плагин перехватить или подменить чужие ссылки
  (OAuth, `tg://`), и с какими правами.

## Этап 6 — UI, настройки, shim-слой (опционально)

Наименьший приоритет. Гнать, если остались лимиты.

Скоуп:

- Java: оставшееся в `ui/` (`PluginsActivity`, `PluginSettingsActivity`,
  `PluginsInfoActivity`, `components/PluginCell`, `SafeModeBottomSheet`,
  `templates/*`), `models/*`, shim-классы в `com/exteragram/messenger/plugins/`,
  `proguard-rules.pro` (только правила для плагинов).
- Python: `ui/settings.py`, `ui/alert.py`, `ui/bulletin.py`,
  `extera_utils/text_formatting.py`, `markdown_utils.py`.

Ключевые вопросы:

- Shim-слой: не выставляет ли shim внутренние методы, которые позволяют обойти
  проверки (например, включить плагин, выдать грант, сменить режим)?
- Рендер данных плагина (имя, описание, иконка, HTML/markdown): подмена UI,
  выдача себя за системный диалог, кликабельные ссылки и интенты.
- Настройки: может ли плагин через `CustomSetting` / `UniversalFragment` открыть
  экран, который выглядит как экран разрешений?
- Крэши UI на кривых данных плагина.

## Этап 7 — Сводка

Вход — только `review/*.md`, код не читается (кроме точечной проверки спорных
находок). Можно отдать модели подешевле.

- Дедуп, единая нумерация, пересчёт severity с учётом цепочек между этапами
  (например, «утечка из этапа 5 + обход из этапа 2 = Critical»).
- Отметить находки с уверенностью `speculative`, которые стоит перепроверить.
- Итог — `review/SUMMARY.md`: таблица находок по приоритету и порядок
  исправления (что фиксить первым, что можно чинить вместе).
